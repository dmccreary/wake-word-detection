# Lab 1: Setup and Wiring

**Time:** ~60 minutes  |  **Prerequisites:** a working wake-word detector from [Real-Time DSP on a $5 Microcontroller](https://dmccreary.github.io/fft-benchmarking/)  |  **Hardware:** the full kit

## What You'll Build

A single program that steps through all five peripherals — LED, display, buttons, microphone,
speaker — and proves each one works before you build anything on top of it.

This is deliberately the least clever program in the course. Its value shows up in Lab 3, when
the wake-word detector fails to hear you and you already know, for certain, that the microphone
is fine.

## Learning Objectives

- **Wire** an I²S microphone and an I²S amplifier to the same board
- **Explain** why those two devices cannot share one I²S bus
- **Describe** what the `ws = sck + 1` constraint is and where it comes from
- **Centralize** every pin number in one `config.py` instead of scattering them
- **Verify** each peripheral independently before combining them
- **Distinguish** a wiring fault from a software fault

## Concepts Introduced

| Concept | What it means here |
|---|---|
| I²S bus direction | Data lines carry audio one way only — in or out, never both |
| I²S clock lines | Bit clock and word select, generated by whichever device is master |
| I²S master and slave | Both our audio chips are slaves; the Pico must clock both |
| PIO sideset pins | How the RP2350 generates I²S clocks, and why pins must be adjacent |
| Half-duplex peripheral | One `machine.I2S` instance is RX **or** TX, never both |
| Hardware configuration module | One `config.py` as the single source of truth for pins |
| Falling-edge button input | `PULL_UP` means a press reads 0, not 1 |
| Peripheral smoke test | Proving hardware before trusting software |

## Background

### The kit gains an output

The prerequisite course only ever *listened*. Every lab in it ended with a number on a screen.
This course has to **talk back**, which adds two things to the kit: a MAX98357A class-D
amplifier and a small speaker.

That turns out to raise a question almost every student asks within about ten minutes of
looking at the wiring diagram.

### Why can't the microphone and the speaker share one I²S bus?

It's a fair question. I²S is a *bus*, and buses normally allow several devices on one set of
wires. The INMP441 speaks I²S. The MAX98357A speaks I²S. So why does the wiring table below use
six GPIO pins instead of four?

The answer has three layers, and each one alone is enough to settle it.

#### Layer 1 — the data lines are opposite directions

An I²S connection is three wires:

| Wire | Name | Job |
|---|---|---|
| SCK / BCLK | Bit clock | ticks once per bit |
| WS / LRC | Word select | marks the sample/channel boundary |
| SD / DIN | Serial data | the audio bits themselves |

The two clock lines are shared-able in principle — that is exactly how a normal multi-device
I²S bus works, with one master clocking several peripherals.

The **data** line is not. On the INMP441, `SD` is an *output*: the microphone drives it. On the
MAX98357A, `DIN` is an *input*: the amplifier listens to it. They point opposite ways, so they
are two separate wires no matter what else you do.

So even in the best possible case, sharing saves you **two** jumper wires, not three.

!!! note "Tying them together does something, just not something useful"
    Physically joining the mic's `SD` to the amp's `DIN` is not a short circuit — it is a
    loopback. The speaker would play whatever the microphone hears, continuously, with no
    software involved. It's a fun five-minute demo and a screeching feedback loop, but it is
    not a signal path any program can use.

#### Layer 2 — stock MicroPython won't let you share the clocks either

This is the part specific to our hardware, and it is the real answer.

On the RP2350, `machine.I2S` is not a dedicated hardware peripheral. It is built out of **PIO**
— the programmable I/O blocks — and each `I2S` object claims its own PIO state machine that
**generates** the clocks itself. From MicroPython's `ports/rp2/machine_i2s.c`:

```c
#define MAX_I2S_RP2 (2)

typedef enum {
    RX,
    TX
} i2s_mode_t;

if (ws != (sck + 1)) {
    mp_raise_ValueError(MP_ERROR_TEXT("invalid ws (must be sck+1)"));
}
```

Three facts fall out of those few lines:

1. **There are exactly two I²S instances**, `id=0` and `id=1`.
2. **Each instance is half-duplex** — `RX` or `TX`, never both. One instance cannot serve a
   microphone and a speaker at the same time.
3. **`ws` must be `sck + 1`.** The comment in the source explains why: *SCK and WS are
   implemented as PIO sideset pins, and sideset pins must be sequential.*

That third point is the one that closes the door. Because each instance generates its own SCK
and WS, pointing both instances at the same two GPIO pins does not create a shared bus — it
creates **two independent state machines driving the same wires**, with no phase relationship
between them. That's pin contention, and the result is garbage on both.

Neither chip can rescue you by supplying the clock instead: the INMP441 and the MAX98357A are
both I²S *slaves*. Someone has to be master, and the only candidate is the Pico.

!!! warning "The `ws = sck + 1` rule constrains your pin choices"
    This is a hard error, not a warning, and it bites people who pick pins by what's physically
    convenient on the breadboard. Both buses in this kit obey it — mic `SCK=10, WS=11` and
    speaker `BCLK=16, LRC=17`. If you re-map pins in `config.py`, keep each clock pair
    **adjacent and in that order**, or `machine.I2S` raises
    `ValueError: invalid ws (must be sck+1)` at construction.

#### Layer 3 — you wouldn't want to share them anyway

Suppose the constraint above vanished tomorrow. Sharing would still be the wrong design for
this kit, for three reasons that matter later in the course:

- **The two devices run at different sample rates.** The microphone captures at 12,800 Hz to
  match the wake-word frame budget. Cloud text-to-speech typically returns audio at 16,000 Hz.
  One shared clock cannot serve both without resampling one of them in software.
- **A shared clock is always running.** The MAX98357A plays whatever sits on `DIN` whenever it
  is clocked. You would have to feed it a continuous stream of silence the entire time you were
  merely *listening*, or accept hiss from the speaker.
- **Separate buses let you switch the speaker off completely.** Because the amplifier owns its
  own peripheral, the code can `deinit()` it while listening and re-create it to speak. That is
  precisely the mute-and-resume behavior this course needs when it tackles the device
  re-triggering on its own voice.

!!! tip "It *is* possible — just not within this course's rules"
    You can implement genuine full-duplex I²S on one clock pair by writing your own PIO
    program, and people do. That means bypassing `machine.I2S` entirely. This course, like its
    prerequisite, runs on stock MicroPython with no toolchain, so we spend two extra GPIO pins
    instead of a custom PIO assembler. Knowing *which* constraint you're paying for is the
    point.

### One file owns every pin

Nothing in this kit hardcodes a pin number except [`config.py`](https://github.com/dmccreary/wake-word-detection/blob/main/src/config.py).
Every lab imports it. Re-wiring the kit means editing one file, and a lab that runs on your
bench runs on someone else's differently-wired bench without modification.

## Wiring

Two independent I²S buses, plus SPI for the display and three plain GPIO inputs:

```
                     ┌────────────────────┐
   GPIO 10  ────────►│ SCK                │
   GPIO 11  ────────►│ WS      INMP441    │   I2S id=0, RX  (Pico listens)
   GPIO 12  ◄────────│ SD                 │
                     │ L/R ── GND         │
                     └────────────────────┘

                     ┌────────────────────┐
   GPIO 16  ────────►│ BCLK               │
   GPIO 17  ────────►│ LRC     MAX98357A  │   I2S id=1, TX  (Pico talks)
   GPIO 18  ────────►│ DIN                │
   GPIO 19  ────────►│ SD (shutdown)      │
                     └────────────────────┘

   arrows show which end drives the wire
```

**Display — SSD1306 128×64 OLED (SPI0)**

| OLED | Pico 2 | Purpose |
|---|---|---|
| VCC | 3V3 | power |
| GND | GND | ground |
| SCL / CLK | **GPIO 2** | SPI clock |
| SDA / MOSI | **GPIO 3** | SPI data |
| RES | **GPIO 4** | reset |
| DC | **GPIO 5** | data/command select |
| CS | **GPIO 6** | chip select |

**Microphone — INMP441 (I²S bus 0, receive)**

| INMP441 | Pico 2 | Purpose |
|---|---|---|
| VDD | 3V3 | power |
| GND | GND | ground |
| SCK | **GPIO 10** | bit clock |
| WS | **GPIO 11** | word select — note `11 = 10 + 1` |
| SD | **GPIO 12** | serial data (mic → Pico) |
| L/R | GND | selects the left channel |

**Speaker — MAX98357A (I²S bus 1, transmit)**

| MAX98357A | Pico 2 | Purpose |
|---|---|---|
| VIN | VBUS (5V) | power — see the warning below |
| GND | GND | ground |
| BCLK | **GPIO 16** | bit clock |
| LRC | **GPIO 17** | word select — note `17 = 16 + 1` |
| DIN | **GPIO 18** | serial data (Pico → amp) |
| SD | **GPIO 19** | shutdown, optional |
| `+` / `−` | speaker leads | 8Ω speaker |

!!! warning "Power the amplifier from 5V, not 3V3"
    The MAX98357A will run off 3V3, but quietly — its output power scales with supply voltage,
    and the Pico's 3V3 regulator is not sized to drive a speaker on top of everything else.
    Use **VBUS** (pin 40, the 5V rail from USB). A loud amplifier browning out the 3V3 rail
    mid-sentence produces bugs that look like software faults and are not.

!!! note "The amplifier's SD pin is optional but useful"
    Left unconnected, the MAX98357A uses its default gain and is always enabled. Wiring it to
    GPIO 19 lets software shut the amplifier off completely — the hardware half of the
    mute-and-resume mitigation later in the course. Set `SPK_ENABLE_PIN = None` in `config.py`
    if you leave it unwired.

**Buttons — three momentary push buttons**

| Button | Pico 2 | Role in this lab |
|---|---|---|
| MODE | **GPIO 13** | advance to the next check |
| UP | **GPIO 14** | volume up |
| DOWN | **GPIO 15** | volume down |

Each button's other leg goes to **GND**.

!!! note "A press reads 0, not 1"
    `Pin.PULL_UP` holds each pin at 1 until a press drags it to 0, so a press is a **falling**
    edge. Nearly everyone writes `if button.value():` the first time and wonders why the
    program reacts when they *let go*.

## Procedure

### Step 1 — Upload the kit

From `src/`:

```bash
./upload-code.sh
```

Quit or disconnect Thonny first — only one program can use the Pico's serial port at a time.

### Step 2 — Run the setup program

```python
--8<-- "src/labs/01-setup/01-setup.py"
```

### Step 3 — Work through the five checks

Press **MODE** to advance. Each check is designed so that a wiring fault has an obvious symptom:

| Check | What you should see | If it fails |
|---|---|---|
| 1. LED | Onboard LED blinking | The program isn't running at all |
| 2. Display | An outline box, a filled box, a diagonal line | SPI wiring |
| 3. Buttons | `U`/`D` appear while held; press count rises | Button wiring or missing GND |
| 4. Microphone | Peak % rises when you speak | Mic wiring or L/R not grounded |
| 5. Speaker | An 880 Hz beep; UP/DOWN change volume | Amp wiring or power |

### Step 4 — Confirm the microphone actually responds

The microphone check is the one worth lingering on. In a quiet room the peak should sit low.
Speak, clap, or whistle and it should jump by more than 10×. A meter that reads a *constant*
non-zero value no matter what you do usually means DC offset is not being removed — which is
what `config.read_samples()` exists to handle.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `ValueError: invalid ws (must be sck+1)` | Clock pins not adjacent | Each I²S clock pair must be `sck`, then `sck+1` |
| `OSError` opening the second I²S | Both I²S ids already in use | Only two exist; `deinit()` one before opening another |
| Microphone reads all zeros | L/R floating, or SD miswired | Tie L/R to GND; check SD → GPIO 12 |
| Microphone reads a big constant | DC offset not removed | Use `config.read_samples()`, not raw words |
| Speaker silent | Amp unpowered or SD pin held low | VIN → VBUS; check GPIO 19 is driven high |
| Speaker quiet and distorted | Amp running off 3V3 | Move VIN to VBUS (5V) |
| Speaker hisses constantly | Amp clocked with no data | Expected between beeps; `deinit()` when idle |
| Buttons react on release | Testing for 1 instead of 0 | `PULL_UP` means a press is a falling edge |
| Display blank | SPI wiring, or RES not connected | Verify all five display pins |

## Challenges

1. **Break the rule on purpose.** In `config.py`, change `SPK_WS_PIN` to 18 and run any program
   that opens the speaker. Read the exact error. Now you'll recognize it instantly when it
   happens for real.
2. **Count the pins.** The kit uses six GPIO pins for two I²S buses. Work out how many it would
   use if sharing clocks were allowed, and how many wires that actually saves.
3. **Measure the rate difference.** `config.py` sets the mic to 12,800 Hz and playback to
   16,000 Hz. If you had to share one clock, which would you change, and what would it cost?
4. **Move a bus.** Re-map the microphone to a different pair of adjacent pins, edit only
   `config.py`, and confirm every lab still runs untouched.
